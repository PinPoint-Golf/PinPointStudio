## 2. Premises I think are wrong, or that no longer hold

1. **"Test targets that hand-list sources: to 0."** The plan's libraries are Platform, Vocabulary, Rules, Domain model and the stores. 141 of the 249 hand-listed sources are Adapters files, and only the stores' 25 are in a planned library. After all five libraries, about 120 executables still hand-list about 770 sources: `Gui` 497, `Ppcp` 105, `LaunchMonitor`'s connectors 72, `App` 39, `Analysis`' pipeline 33, `IMU`'s back-ends 11. Reaching 0 needs libraries for `Gui`'s presenters and `Ppcp`, which is Stage D's, E's and F's ground. **Proposed (P1):** "hand-listed sources that belong to a ring library: 0", enforced by a check (B2.4), with the rest counted and named.
2. **"The case for libraries is enforcement, not rebuild time" (Premise 3, §10 row 2.1c).** Row 2.1c is about the app's rebuild pain (ccache and the QML-cache fix), and for the app the sentence stands: it compiles each file once. It understates the test tree, where the studio PC's clean build is 5,614 compiles and 5,698 of the Mac's are the same 249 sources again and again (`pp_log_stream.cpp` 177 times, each Diagnostics norm source about 140). With the five libraries the clean build is about 250 + 770 + 347 test files: roughly 1,400 compiles, a quarter. The header rows fall with it. This is the stage's largest measurable gain and the plan does not claim it. The link row can get worse: 356 links each read large archives.
3. **"One static library per ring."** The test tree is built "WITHOUT … whisper/ggml, FFmpeg, espeak" (`tests/CMakeLists.txt:4`) and has no ONNX Runtime. So: `Core/pp_debug.cpp` (whisper, ggml, `QMediaPlayer`) can't join `pp_platform`, as the pilot found; 12 Rules sources are never compiled there (the three pose estimators and their base, `pose_runner`, `person_segmenter`, `ball_runner`, `impact_runner`, and four `Club` files); `Export`'s FFmpeg encoder and exporters likewise. 33 Rules files include OpenCV, which only some tests link. A Rules library that every Diagnostics test links must not drag OpenCV in, so Rules is cut as `pp_rules` (Qt and Eigen) and `pp_rules_vision` (OpenCV). That is a split by third-party need, not the ruled "context seam" (L6), so it is a question (L7), not a call.
4. **"Until Stage D, `Buffer`, `IMU` and `Pose` still span rings."** After Part 1 as ruled, so do `Gui` (`Gui/shot`'s six files), `Core` (`device_enumerator`, R4), `LaunchMonitor` (by sub-folder, R5) and **`Analysis`**: twelve Rules stems, the pipeline (Application) and `mp4_frame_reader` (Adapters) in one directory. No stage owns `Analysis`' split, so "8 → those Stage D owns" leaves one with no owner. **Proposed (L8):** the Rules library takes `Analysis`' Rules files by name, as the plan allows for the other three, and the directory's split is given an owner.
5. **"Its include directories are `PRIVATE`."** The pilot exports `src/Core` to its users (`PRIVATE` + `INTERFACE`, `PUBLIC` in effect), because 370 files include `Core` and many by bare name. A library whose own files resolve every include relatively needs no include directory at all; what it *exports* is a separate choice (L2). The accept figure "in library files: 0" tests the first; the second is for the Solution Architect.
6. **"The quoted includes … are rewritten as each library is cut, in the same pass as the Vocabulary move's."** Only 59 of the 425 are in the libraries' own files (Rules 49, the stores 7, Vocabulary 3). The other 366 are the executable's (`Gui` 273). So the rewrite inside Part 2 is small, and the 425 barely moves unless B2.21 trims the app's directories.
7. **"Tests link libraries instead of hand-listing sources" as one bullet.** It is seven items (B2.12–B2.16): the lists share variables (`NORM_SRC` and others in `src/Analysis/tests/CMakeLists.txt`, 2,624 lines, 140 hand-listing executables), and a test that both lists a source and links its library is a duplicate symbol on MSVC and a silent pick on the Mac.
8. **The Test row's "Windows Debug and Release links".** The studio PC has two trees and "never a third" (`studio-build.cmd:12`): the Debug test tree and the Release app tree. So there is no Windows Debug link of the app; the Debug link is the test tree's. The Release app build installs over the studio's app (PR-29). `studio-build.cmd tool` links `swinglab_run` in the Release tree with a patch and installs nothing, which covers every library once the offline tools link them; the app's own Release link needs a new mode (B2.1).
9. **"The three build times against their baseline"** per item: `build_times.sh` builds origin/main's tip with no patch, so an item can't be timed before its commit. Timings are the coordinator's, on main, three times in the stage.
10. **The four test stubs** (`src/Analysis/tests/imu_test_stubs.cpp`, `src/Gui/tests/session_clock_stubs.cpp`, `reanalysis_stubs.cpp`, `src/Ppcp/tests/ppcp_host_service_stubs.cpp`) replace `EventBuffer::nowMicros`, one `AthleteController` method, `reanalyzeShot` and eight `Video` symbols. None is in the five libraries, so no relink meets one today. `pp_log_stub.cpp` has no user (the pilot's Q4).
11. **B-14 ("Diagnostics is not a library target")** is closed by B2.6 as a part of `pp_rules`, not as a library of its own. If the Solution Architect wants a `pp_diagnostics` target, that is L7's answer; `Wrist`'s engine and the norm stack include each other, so the two can't be separate libraries without a cycle.
