# Uncertainty Census — Design Brief

**Status:** brief, not started. Written 2 October 2026.
**Owner:** Mark.
**Gate:** this must be done **before validation and before the first full public release**. It is not required for the beta.
**Prerequisite:** camera calibration status flowing through to the metrics it affects, a separate session (see §6.1).
**Builds on:**
- `shaft_uncertainty_propagation_design.md`: the shaft metrics, implemented 1 October 2026;
- `session_diagnostics_design.md` §A8: σ through the diagnostics DAG, implemented 1 October 2026;
- `body_rotation_estimation.md` §7: the two-camera rotation route and its σ.

---

## 1. Why this exists

The shaft work and §A8 made uncertainty a first-class part of the pipeline. A reading's σ now reaches the probability that a characteristic fired, the session's pattern counts and the ranking of root causes. That chain is only as honest as the σ fed into it.

On 2 October 2026, the 58 metric keys on the 4 July session broke down as follows:

| What they carry | Metrics |
|---|---|
| A per-reading σ: the shaft and club metrics, and the two-camera rotation series | 16 |
| Only frame-to-frame noise (sigmaKind Unspecified), which is a lower bound on the error | 22 |
| No σ at all | 20 |

Examples of noise-only: pelvis sway, spine side bend, shoulder plane, tempo, the four angular speeds. Examples with no σ: knee flexion, spine forward bend, head sway and tilt, stance, ball position, pelvis thrust, foot flare.

For 42 of 58 metrics, then, the diagnostics still give a hard yes/no, or a falsely confident probability. A characteristic built on one of those fires as hard at its edge as far beyond it.

**Validation cannot be honest on top of that.** A validation study compares readings to truth. If the readings carry no stated uncertainty, there is nothing to check coverage against. The study can only report errors after the fact, not test whether the app's own statements about confidence are true.

**A public release should not ship a confidence it has not stated.**

## 2. What the census must produce

### 2.1 One row per metric

The census covers every metric key the pipeline can emit, about 80, including device-sourced (`lm.*`, `hm.*`) and IMU-routed ones. Each row records:

| Field | Content |
|---|---|
| Key, route(s) | From the catalogue: which acquisition routes produce it (face-on, the camera pair, IMU, device) |
| Inputs | What it is computed from (keypoints, the shaft track, the ladder, the ball, skeleton3d, IMU streams) |
| Error sources | Every source in §3 that applies, each marked as a **noise** term (random, shrinks with averaging) or a **bias** term (systematic, does not average out) |
| Propagated today | Which of those sources reach the published σ, and how (closed form, Monte Carlo, bootstrap, frame noise, none) |
| sigmaKind today | Unspecified / Propagated / Calibrated / AssumedInput |
| Gross-error channel | Whether it carries a gross risk, or relies only on an implausibility gate |
| Truth available | What independent truth exists in the corpus to calibrate it (hand marks, launch monitor, HackMotion, none) and how much (n swings, n sessions) |
| Consumers | Measures, characteristics and cards that read it, and which of them are scored |
| Severity | Size of the unpropagated error relative to the corridor it is graded against: high / medium / low |
| Plan | The stage in §4 that fixes it, or a stated reason it is left (and how the card says so) |

### 2.2 Deliverables

1. **A census table**, `docs/research/data/uncertainty/census_<date>.csv` plus a readable `census_<date>.md`. It is regenerated by a script from the catalogue and a swept corpus, so it never goes stale by hand.
2. **A design note for the fixes**, in the style of `shaft_uncertainty_propagation_design.md`: a model per error source, a σ budget per metric family, calibration against whatever truth exists, and stages with gates fixed in advance.
3. **The implementation of those stages**, delivered the same way as the shaft work: one session per stage group, gates first, commits after Mark has seen the graded results, then a library re-analysis and ledger regrade so it can be tested in the app.
4. **A release statement** for the documentation: for each scored characteristic, how confident its firing can be, and what the remaining unpropagated sources are.

## 3. Error sources to inventory

These are the known sources as of 2 October 2026. The census should confirm each one and add any it finds.

1. **Camera calibration.** The down-the-line camera's placement is assumed. This affects skeleton3d, shaft fusion and every triangulated metric. It is the prerequisite session (§6.1), but the census must record which metrics it touches.
2. **Pose keypoint error beyond frame jitter.**
   - The pose smoother's per-keypoint σ (`PoseKpAux::sigma`) is used only by the shaft budgets.
   - Hand-keypoint confidence lies on this pose model.
   - Joint label swaps and mis-locks have no gross-error probability, the way the shaft tracker's samples do.
3. **Event timing.**
   - Body metrics read at Address, Top, Impact or a P-position carry no timing term. The phase ladder records no σ of its own (only the shaft's P-positions carry `sigmaTUs`).
   - Address timing is a bias on every address-relative metric.
   - There are three different impact instants, with the 13–22 ms trigger bias; `uncertainty.oneImpact` is built and dark.
4. **Single-camera projection.**
   - Face-on metrics assume the golfer is square to the camera at address.
   - They read 3-D quantities as their frontal projection: lateral quantities absorb rotation after impact, and sagittal ones foreshorten.
   - `MetricDescriptor::stereoGain` documents which metrics this affects, but it is a bias, and nothing carries it.
5. **Scale.**
   - The ball-diameter ruler (5%) is used only in low point.
   - skeleton3d's default golfer height.
   - The default club length, propagated for speed only.
   - Every distance metric in mm or cm depends on one of these.
6. **Camera timing and optics.**
   - Frame quantisation (±4 ms at 120 fps).
   - Host-stamped frame times (±0.4 ms).
   - Motion blur from the 6.5 ms exposure, the main noise source for low point and attack angle.
   - Rolling shutter and lens distortion.
   - The face-on/down-the-line clock offset.
7. **The norms themselves.** P(fire) treats a corridor's edge as exact. Many norms are marked heuristic or provisional, so their centre and width are uncertain too, and an uncertain edge should widen P(fire). This is distinct from the norm's population σ, which places the edge.
8. **Launch-monitor readings taken as truth.** `lm.*` values carry no σ. The GC Quad over-reads clubhead speed by about 2 mph at 70–100 mph.
9. **IMU readings.** The IMU routes leave σ unset. Filter drift, mount and anatomical-calibration error, and the integrity check (which no Witmotion swing has ever passed) do not reach any reading.
10. **Model structure in the diagnostics** (already listed as gaps in `session_diagnostics_design.md` §A8.8):
    - correlation between the signals of one shot;
    - shots that are not independent;
    - the inferred-context confidence (0.7), not folded into P(fire);
    - the link 2×2 on hard counts;
    - uncalibrated strength and prominence words.
11. **skeleton3d's posterior σ.** It assumes the rigid model and its priors are right, so it is probably optimistic. The high thorax readings on 4 July (about 103° at the top) are a candidate example.
12. **Smoothing and reducer bias.** The windowed median at phases and the 40 ms windowed-mean extremum pull peaks toward the mean. That is a bias, not noise.

## 4. Method

1. **Generate the skeleton of the table automatically:**
   - keys, routes and consumers from the metric catalogue and `core.json`;
   - what each metric carries today, from a swept corpus, as in the 2 October count;
   - truth availability from `truth.json`, launch-monitor pairs and HackMotion sessions.
2. **Fill error sources and propagation by reading each producer**, the way the shaft developer guide was written. One family at a time: setup, lower body, upper body, head, rotation, club delivery, kinematics, device.
3. **Measure, don't assume, where possible.**
   - Repeatability across still address frames gives noise floors.
   - Shot-to-shot spread within a session gives an upper bound on noise.
   - Two-route agreement (face-on vs the pair, the pair vs IMU) bounds bias.
   - Hand marks and the launch monitor give coverage where they exist.
4. **Rank by severity:** the unpropagated error's size against the width of the corridor the metric is graded by, weighted by whether its characteristics are scored.
5. **Plan the fixes in stages.** The likely order:
   - pose keypoint σ and gross risk for the body metrics, together with event-timing σ (§3 items 2 and 3, which cover most of the 42 metrics);
   - scale;
   - norm-edge uncertainty in P(fire);
   - device and IMU σ.

   Every stage gets the same treatment as the shaft work: verdict and value identity when off, held-out coverage when on, and moved readings listed for Mark.

## 5. Definition of done

1. Every metric key the pipeline can emit has a census row. No row is blank in "error sources" or "propagated today".
2. Every **scored** characteristic's measures carry a per-reading σ that is either:
   - checked against independent truth (calibrated), or
   - propagated from calibrated inputs, with the remaining unpropagated sources named in the release statement.
3. Every metric that still carries no σ says so on its card ("uncertainty not characterised"). Absent never reads as exact.
4. The census script runs in CI or as a documented tool, so the table is regenerated rather than maintained.
5. The validation protocol (`two_camera_capture_protocol.md` and its successors) cites the census for what each measurement's stated σ is, so validation tests coverage, not just error.

## 6. Dependencies and order

1. **Camera calibration status flowing through to the metrics it affects.** This is a separate session, and first: a calibrated pair changes the σ of every triangulated metric. The skeleton3d route already has the hook (`TriangulatedTurnInput::camerasCalibrated`); shaft fusion and skeleton3d itself need theirs.
2. **This census.**
3. **The fixes it plans.**
4. **Validation.**
5. **First full public release.** The beta does not wait on this.
