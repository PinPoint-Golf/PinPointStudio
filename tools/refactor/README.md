# tools/refactor — the move tool

`move_files.py` makes every scripted move of the platform refactor (Stage B; the rules are `build/platform/B1/MOVES.md`): files and folders under `src/` move to new homes, and every include, build-file line, lint table key, allowlist key, tool path and doc path that names them follows. A move is a map file, so another lane can replay it over its own work, and a reviewer reads the map and `--verify`'s summary instead of a 300-file diff. Python 3, standard library only. `context_check.py` is the kept copy of the context-map check (below).

## Writing a map

`tools/refactor/maps/<item>.map`, one move per line, paths from the repo root, `#` for comments:

```
src/Metrics/ -> src/Vocabulary/Metrics/          # a folder: every file under it, tests/ included, listed at run time
src/Core/club_standards -> src/Vocabulary/Club/  # a stem: its .h, .cpp and .mm, whichever exist
src/Export/frame_decode.h -> src/Vocabulary/Recording/   # one file
```

A destination ending in `/` keeps the file name; `→` works as well as `->`. A line `keep: <file>:<line>[-<line>][,…]` names lines the move leaves exactly as they are: a dated record, such as a decision or a change-log row, must say what was true then. Only in docs (`docs/`, `*.md`): a keep on a build, C++ or tool line is an error, since it would hide a stale path no later check sees. A keep must match a line the tool reads: one on a doc it does not scan (`docs/implementation/`, a `.md` under `src/`) is an error too, not a silent no-op. The docs it scans are `docs/developer/`, `docs/design/`, `governance/` (its `.md` and `.txt`; `tokens.json` is generated), `BUILDING.md`, `README.md` and any `.md` under `tools/` (not this README or the maps), `packaging/` or `.github/`. The map is the only source: there is no command-line keep, so a verify reads the keeps the move read and can't be loosened by hand. The report lists each one with what the move would have made it; `--verify` passes the old spelling on exactly those lines, names each, fails if one changed at all (in an `--allow-prose` file too: it finds each kept line through the file's diff, so a row added above it by hand moves it, not the check), and still fails an old spelling anywhere else. Line numbers are those of the tree before the move; a kept line the map would not rewrite is an error (a stale number). Never write a count into a map: the tool lists folders from the tree when it runs. File and stem lines are expanded before folder lines, so a file moved into a folder another line also moves is not claimed twice. A folder can't move into itself or its parent.

## The four modes

- **`move_files.py <map> --dry-run`** prints the report and changes nothing (the self-test checks every byte): the files to move; each include line to rewrite and how it resolved (`rel` relative to the file, `src` under `src/`, `gui` under `src/Gui/`, `base` only by a unique basename, that is through an include directory); the outward includes inside moved files; the includers of the moved set in `src` and `tools` (the scope of `build/platform/B1/count_includers.py`, so the two figures compare); path mentions by kind (build, lint, allowlist, context, tool, doc, comment); include directories re-pathed; each moved file whose lint ring or `context_check.py` context changes; what it can't place; and the errors. Exit 1 if there are errors.
- **`move_files.py <map>`** does it: the rewrites, then `git mv`, then removes the emptied folders. It refuses while the report has an error, and refuses a dirty tree (`git status`) unless `--over-work` is given, which is how another lane replays a committed move over its uncommitted work. It is idempotent: a second run moves and rewrites nothing.
- **`move_files.py <map> --verify <base commit>`** checks the working tree against the commit before the move, on its own reading (it pairs files by the map, not by git's rename detection, and shares only the token grammar with the rewriter): every moved file is at its new path and every other file at its old one; each changed line is an include line whose target in the base, moved by the map, is its target now; or a line where only path words changed, each naming in the new tree the map's image of what it named in the base (in C++ and QML/JS, only inside a comment); or an include directory removed from a build file. Every include that resolved in the base resolves to the image of its target, never through an include directory or `src/Gui/` alone. The allowlist keeps its number of entries, each rule and count, with keys re-keyed. A binary file must be byte-identical and a file's mode unchanged (the mode is not checked on Windows). It ends with the rewriter's own pass over the result: a file still to move, or an include or mention still to rewrite (a stale spelling on a line the diff never touched), fails. Listed, not failed, for the reviewer: a hand edit on a line of the lint's tables or of `context_check.py`'s `DIRS`/`FILES`/`L2_GAP` (an entry deleted because a folder rule now covers it, a ring or tag changed or added, a comment), and a re-key still pending on such a line; a change under `tools/refactor/` (the tool and the maps, committed with the move); a doc named with `--allow-prose <file>` (the IM rows a brief names); and, with `--allow-code-path <file>:<lines>` (for example `src/Vocabulary/Metrics/gate_catalogue_rules.h:38-42`, B1.6's), a path in a C++ string changed to the map's image on exactly those lines of that file. Anything else is printed and the exit is 1. A changed build-file word that brings in a `${VAR}` its line can't see (set only in a sibling folder, or later in the file: B1.18's F1) fails with its own message.
- **`… --verify <base> --configure <scratch dir>`** is the independent proof of the build files: after the line checks it runs `cmake -S <root> -B <dir>/app` and `cmake -S <root>/tests -B <dir>/tests`, prints each CMake error, and exits 1 if either tree fails to configure. It is a heavy job: run the whole call through `build/refactor/one_at_a_time.sh`, on a scratch copy, into an empty folder (it refuses one that is not). `--seed <build dir>` (default `<root>/build`) names a configured checkout's build folder: its `app/` and `tests/` caches give the generator, `CMAKE_PREFIX_PATH`, ccache, `PP_OPENCV_ROOT` and every `FETCHCONTENT_SOURCE_DIR_*` (or a `<name>-src` it fetched), and its `_deps/` downloads (the models, yt-dlp) are cloned in, so the configure downloads nothing the seed has. `--cmake-arg <arg>` passes one more argument to both, whatever it starts with (`--cmake-arg -DPINPOINT_BUILD_TOOLS=ON`), after the seed's, so it wins; the seed also carries `PINPOINT_BUILD_TOOLS` and `PINPOINT_BUILD_LM_REPAIR`. A tree with no `CMakeLists.txt` is FAILED, never skipped. **`--verify` without `--configure` is not a pass** (B1.2b): it prints `NOT CONFIGURED: this is not a pass` and exits 3 (1 if the line checks failed too). `--no-configure-ok` turns that off, for the self-test only; a move's NOTES always carry `CONFIGURE PASSED`.
- **`move_files.py --self-test`** builds a small git repository in a temporary directory and proves each rule and each refusal: a folder and a stem move; includers in each spelling, an `#import`, an outward include, a bare include that relied on a global or a test's own include directory (`INCLUDE ${SRC}/Metrics`); a CMake list and its variables; a lint table; an allowlist line; `context_check.py`'s tables; an ambiguous basename (refused); a dirty tree (refused); idempotence; and `--verify` passing on the move and failing on each of a retargeted include, a deleted include, a code line changed in a moved file, an added allowlist line, an added include directory, a line-ending change, a table line deleted outside the lint, a path changed in a C++ string, and a file moved that the map doesn't move. A second fixture proves the CMake scopes (B1.2a): B1.18's case (a path moved under `src/Gui/` from `src/Analysis/tests`, where `${GUI}` is set only in the sibling `src/Gui/tests`) is respelt `${SRC}/Gui/…`; a variable from an `include()`d file and from the parent before `add_subdirectory()` is used, one the file sets on a later line is not; `--verify` fails on `${GUI}` written there and on a variable used before its line; and, when cmake is on the PATH (not on Windows), `--configure` passes both of the fixture's trees (two `project(… NONE)` lists, under a second), fails when the test tree does not configure, and refuses a folder that is not empty. A third fixture proves the constructs (B1.2b), each line left as it was and listed as can't place with its reason, or rewritten where the walk can decide: a function body called with two values of a variable (can't place), called once after the variable is set (rewritten; the second fixture configures it, and `--configure` fails on the old definition-site reading), called from two folders with a relative path, and never called; a set and an `include()` under an undecided `if` (known inside the branch, can't place after `endif`); a macro's set (rewritten); `unset()`; a `return()` on some paths (can't place) and on every path (the set after it never runs); a child's `PARENT_SCOPE` set (rewritten) and one under an undecided `if` (can't place); `--verify` lists each and fails on a rewrite through an undecided variable. It also proves a can't-place line left whole, `--verify` listing the base reading's can't-place lines, and `keep:` (the kept line unchanged and listed, `--verify` passing it, failing the old spelling on the next line and any change to the kept one, finding it under `--allow-prose` after a line added above; a stale keep, a keep on a build or C++ file, a keep on a doc the tool does not scan, and `--keep` on the command line each refused), a `governance/` doc's path rewritten and its keep held (its `tokens.json` left alone), `--verify` failing an old spelling left there, and, with cmake, that a `--cmake-arg -D…` reaches both caches over the seed's value. That fixture runs no cmake, so it runs on Windows too. ctest: `move_files_selftest` (`src/Gui/tests/CMakeLists.txt`; 77, a skip, without git).

`--root <checkout>` runs on another checkout; `--quiet` prints totals only. The report also lists each build file the CMake walk does not reach (a `cmake -P` script): it is read with its own sets only.

## How it resolves and rewrites

Includes resolve as lint A1 does (`architecture_lint_test.cpp`, `resolve()`): relative to the including file, then under `src/`, then under `src/Gui/`, then by basename when it is unique. The tool's basename table also holds test files, so it is stricter: a name shared with a test header is ambiguous. **An ambiguous basename is an error, never a pick.** A path under `src/` or `src/Gui/` keeps its style; anything relative is recomputed from the file's new home; anything that resolved only through an include directory becomes the relative path. A `<…>` include that names a moved header is an error (rewrite it by hand).

Other mentions are rewritten only when anchored: `src/<old>…`, `${VAR}/…` (read only where CMake gives `VAR` to that line, below; a path that leaves its variable's folder is respelt with the deepest variable the line knows that holds it, then the one the file already spells most, else a repo-root variable it knows, else it is listed under "can't place": never a variable from another folder), `../…` from the file, a build file's path relative to its folder, or `<old folder>/<a real moved file or subfolder>`. A bare old folder name (`Metrics/`, `src/Coaching` read as prose) is rewritten only where every string is a path key: the lint, the allowlist's key column and `context_check.py`. Anywhere else it is listed under "can't place", with mentions of files that no longer exist and paths in C++ string literals. So is a path it can't rewrite because it is split, in `.py`, shell and build files: quoted words joined into an old path (`os.path.join(ROOT, "src", "Metrics", "x.h")`) or a path built in parts (`'Metrics/' + name`). Write such a path as one `"src/…"` string, and a move rewrites it.

**CMake variables: what a line knows** (`CMakeVars`, B1.2a and B1.2b). The tool walks the build the way a configure does, from every `CMakeLists.txt` that calls `project()` (the app's root, `tests/`, each suite that also runs standalone, `src/Buffer`), in statement order. `add_subdirectory()` gives the child a copy of the scope at that line (`foreach()` with literal items expanded, so `tests/` reaches each suite); `include()` reads the file in the includer's scope (a module name through `CMAKE_MODULE_PATH`), and its sets are known after that line; a `CACHE INTERNAL`/`FORCE` set is seen from then on, a cache default is not (a `-D` wins). **A `function()` or `macro()` body is read where it is called**, never where it is defined: a function in a copy of the caller's scope with its arguments (`ARGN`, `ARGV<n>` and the named ones), a macro in the caller's own scope, so its sets change the caller's variables. A body line knows only what every call agrees on (`CMAKE_CURRENT_LIST_DIR` and `CMAKE_CURRENT_SOURCE_DIR` are the caller's there, as in CMake), and a body no call reaches knows nothing. `if(NOT COMMAND x)` and `if(PROJECT_IS_TOP_LEVEL)` are decided; any other condition reads each branch from the state before the `if`, so a first set is known inside its own branch, and after `endif()` a variable the branches (or the branch not taken) leave different is **undecided**. `unset(X)` unsets X (a cache value shows through); `set(X v PARENT_SCOPE)` writes the parent's X after the `add_subdirectory()` or the call, undecided if it runs on some paths only; `return()` ends the file or the function, and one under an undecided `if` leaves every variable set after it undecided for the includer or the caller. A file reached by several routes (the umbrella and standalone, the app and the test tree) knows a variable only where every route agrees on its value: so `${CMAKE_SOURCE_DIR}` is the repo root only in the app's own lists, and `${SRC}` exists only in the suites that set it. **What the walk can't decide is listed as can't place, never guessed** (prefix `CMake scope:`): a `${VAR}/…` word whose undecided VAR, on one of its values, names a moved path; one whose VAR has no value the tool can read and whose tail names a moved path; and a relative path in a body whose calls come from another folder. The real run leaves each such line **whole**, every word on it unrewritten (each word the move would have changed is listed as "left with its line"); `--verify` lists it for the reviewer from the base reading and from the result, so a line whose doubt is gone once moved still shows and fails a rewrite through an undecided variable, and `--configure` is the proof. `--verify` reads the base and the result the same way.

## What it never does

- Add an include directory or an allowlist line. An include directory that names a moved folder is re-pathed in place, never added, and listed: after the run no include of a moved file relies on one, so the brief removes it by hand ("remove a global directory once nothing needs it, and say which").
- Delete a table entry, change a ring or a context. The report lists each moved file whose ring (the lint's `dirRings()`/`fileRings()`) or context (`context_check.py`) changes, or that gets no context tag. Those are the brief's hand edits.
- Change a C++ string literal outside the lint (a path in code is behaviour), QML or JS strings, a namespace, a type, or any file under `docs/implementation/` (dated snapshots), `build/` or `third_party/`.
- Guess. What it can't place is listed, and an error stops the real run before anything changes.

## context_check.py

The kept copy of `build/context-map/check_includes.py` (which git ignores, and which reads only the tree it sits in): the R-CTX-1 check of every cross-context include, with `--src <dir>` to read another tree. Its `DIRS`, `FILES` and other tables key on literal paths under `src/`, so `move_files.py` re-keys them with each map; never build a key at run time. A directory under `src/` whose files get no tag is an error (exit 1), not a default. `python3 tools/refactor/context_check.py [--src <dir>] --list c`.
