# PinPoint Studio requirements

What the app must do for golfers and coaches: each need in their terms, with why, where it stands, and what it rests on. This page is hand-edited; no script writes it.

## Reading guide

1. **The summary** below: how many requirements each area has, and where they stand.
2. **The use cases**, [`use_cases.md`](use_cases.md), organise the same requirements by what a golfer, a coach or a studio owner is trying to do; [`uc-map.csv`](uc-map.csv) maps each requirement to its use cases.
3. **Release readiness.** `python3 tools/history/loc_history.py` draws the readiness heatmap at the top of the growth chart (area by release and MoSCoW), and `python3 tools/method/make_rtm.py` writes the traceability report into `build/rtm/`: each row's status, linked tests and open bugs, and what is still to do for v1. Both read this page and the live GitHub issues; neither is a commit gate.

## Status, release and MoSCoW

| | |
|---|---|
| **Status values** | **done**: in `main`, shipped in a beta build and used for real, with no open blocking bug. **partial**: some of it works; the Evidence column says what is missing. **planned**: not done, and an issue holds the work. **proposed**: nothing is built and no issue holds the work yet. **won't have**: ruled out; the row keeps its id. After a status, **"open bug #n"** names a bug against the row (a done row with an open bug is not ready), and **"to confirm"** means the status itself is not yet judged with confidence |
| **When a status changes** | A row becomes done when its feature has shipped in a beta and been used, and goes back to partial when a bug is filed against it. Edit the row when that happens; no test label, observation record or version bump is needed. Linking a test to a row (`pp_requirement(<test> REQ-…)`, or a `// REQ:` line in a QML test) and a bug to a row (a `Requirement: REQ-…` line in the issue) is a good habit that makes the traceability report useful, not a rule |
| **Release values** | **v1:** two cameras, solid analysis and diagnostics, early access to coaching. **v2:** multiple cameras, verified analysis and diagnostics, better coaching support. Phone support is experimental until at least v2. **later:** nothing beyond v2 can be seen yet. **never:** ruled out of every release. Each v1 or v2 row carries a **MoSCoW** rating (Must, Should or Could) within its release only; a row in later or never carries none. Status is not priority: a done row can be a Could while one not yet built is a Must. *Solid* means built and tested against fixtures, each reading showing how sure it is and its warnings; *verified* means checked against an independent truth (the instrumented wrist, the launch monitor, or marked video) |
| **Ids** | `REQ-<AREA>-n`, never reused; a new requirement takes the next free number in its area. Areas: CAP capture; DEV devices and calibration; ANA analysis and metrics; DIAG diagnostics; COACH coaching and priorities; REV review, replay and reports; LIB the library and athletes; INST install, update and platforms; REL reliability; PERF performance; PRIV privacy; ACC accessibility and ease of use; HON data honesty. `REQ-HOST`, `REQ-CLIP`, `REQ-OPT`, `REQ-BUF` and `REQ-PORT` are used in design documents for other things, so no area takes those names |
| **Sources** | A bare file name is a document in `docs/design/`, `docs/user/`, `docs/reference/`, `governance/artefacts/` or `governance/controls/`. §n is that document's numbered heading. GU-n is a lifecycle guarantee ([`lifecycle_model.md`](lifecycle_model.md) §6); UI-n, DC-n and AD-n are product rules (`governance/controls/product/`); IM DEC-…, OBJ-…, P… and R-… are information-model ids; UC-n is a use case; #n is a GitHub issue |
| **History** | Statuses were first judged by reading the code (`main` `29eec727`, paths updated to `608f0420`) and the studio visit of 25 Nov 2026. On 27 Nov 2026 the "built, not verified" rows became done, except those marked "to confirm" (now partial · to confirm) and those citing an open bug (now partial · open bug). Changes since are in git history |

Add or change a row by editing this page (agree a new or changed requirement with the owner first). Two rules keep it small:

- **A need, not a design.** A requirement says what the golfer or coach gets, and why. The method, the thresholds, the components and the files belong to the design document that implements it.
- **Point, never restate.** Where a lifecycle guarantee (GU-n), a product control (UI-n, DC-n, AD-n) or an information-model rule already says it, the row states only the need, names the rule, and leaves the rule to decide it[^d1d2].
